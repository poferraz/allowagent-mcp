# AllowAgent MCP — Five-Pass Adversarial Audit

## 1. Executive Verdict & 5-Pass Score Table (Baseline vs. Post-Audit)

**Verdict: do not implement the plan unchanged or connect it to live execution.** It describes a useful policy simulator, but its code does not implement a secure MCP reference monitor. Missing parameters bypass verification, approvals can execute altered payloads repeatedly, evaluation mutates the ledger, and several simulated operations misrepresent PayPal. The strongest product direction is a transparent merchant control panel with deterministic verification and explicit approval, plus a clearly labeled consumer simulation.

Hereafter **P:n** identifies a line in that plan, not implemented AllowAgent source. The requested `resources/PAYPAL_DISPUTES_API_COMPLETE.md` is absent; no archived copy was found. The active application remains CaseReady. No application, plan, dependency, or configuration changes were made by this audit.

**Method and coverage.** STATICALLY REVIEWED: every proposed TypeScript/TSX snippet, CSS, fixtures, tests, and Tasks 1–9; authorization boundaries, React behavior, and PayPal mappings. EXECUTED: current repository verification; extracted plan typecheck/tests; 27 adversarial/control cases in an isolated temporary directory using existing dependencies. NOT ASSESSED: live PayPal execution, deployed MCP interception, browser interaction timing, penetration testing, dependency vulnerability scanning, and actual consumer research. UNKNOWN: missing reference contents and real account permissions. Standards: repository rules, TypeScript strict checking, React purity, [CWE-862 authorization](https://cwe.mitre.org/data/definitions/862.html), [CWE-367 TOCTOU](https://cwe.mitre.org/data/definitions/367.html), and official PayPal contracts. ## 2. Pass 1 Findings: Security Loopholes & Default-Deny Hardening (Exact Code Fixes)

**S1 — Critical: the constitution compiler grants absent capabilities and accepts corrupt values. Impact/effort 5/1.** P:675–729. Removing `Allowed Tools` enables all seven tools. `$40.00garbage` compiles as 40; `Price Creep Tolerance: .%` produces `NaN` while `isFailClosed` stays false. Missing `Max Auto-Refund` does not invalidate policy. Unanchored, first-match expressions ignore duplicate/conflicting directives and can consume text from unintended locations; `\s*` can cross lines. Invalid/absent enums silently become defaults. Fix: a documented, line-oriented grammar; exactly one occurrence of each required directive; fully consumed numeric/enumeration values; reject unknown tool tokens and malformed vendor entries. Missing capabilities mean `[]`, never all tools. Reject invalid policy activation and keep previews non-executable. Require valid refund limits even when zero; distinguish intentional empty lists from missing directives. Add deletion, duplication, suffix, empty-list, malformed-percent and round-trip tests.

**S2 — Critical: optional identifiers and agent-claimed identity substitute for positive verification. Impact/effort 5/2.** P:229–267 and P:1420–1664. Every listed tool returns `AUTO_EXECUTE` with `{amountUsd:1}` and no resource IDs when the capability is enabled. Money comparisons accept negative/zero/NaN values; `-39` reduces seeded spend from 28 to −11; NaN poisons the counter. NaN is an internal-JavaScript case, not a valid JSON literal; runtime JSON parsing still requires finite-number validation. A trusted email plus `INV2-SPOOF-99` and amount 1 passes because invoice vendor/total are never bound to the request. A real dispute plus caller-selected `ORD-901` overrides its delivered order. Runtime tool-specific schemas, ownership checks, complete reads, and resource-bound verified facts are mandatory; TypeScript optional properties provide none of these guarantees.

| Tool | Baseline authorization hole | Required positive evidence / safe behavior |
|---|---|---|
| `pay_order` | No order required; recipient check skipped when absent; unknown invoice ignored | Require upstream order ID; read its payee, currency, total, ownership and capturable state; compare those facts to policy. Recipient email is normally absent from the real wire call—derive identity from the order. |
| `record_payment_for_invoice` | Missing invoice skips verification; wrong vendor/amount accepted | Require invoice, payment method and verifiable payment evidence; authorize recording a payment, not transferring money. Validate remaining invoice balance and account scope. |
| `create_order` | No invoice or verified payee needed, yet recorded as spent | An invoice ID is not required by PayPal. Validate all items/totals, merchant context, shipping and redirects; reject unsupported use rather than invent an invoice requirement. Creation is not settlement. |
| `create_refund` | No order skips refund cap; nonexistent orders pass; no capture balance | Require capture ID, owned capture, currency, remaining refundable amount and complete refund/pending-reservation history. Derive full-refund amount when upstream amount is absent. |
| `accept_dispute_claim` | No dispute skips all checks; caller can substitute order; no loss cap | Resolve transactions from the dispute; validate allowed response options and actual liability. Disable by default; require explicit approval and bounded loss. |
| `update_subscription` | Missing/unknown subscription passes; checks fixture's proposed price, not request | Read owned subscription; authorize each requested field, billing-cycle price and resulting recurring exposure. Unsupported fields stay blocked. |
| `cancel_subscription` | Missing subscription passes; price-spike logic incorrectly reused | Require owned, cancellable subscription and cancellation authority. No fake monetary payment; approval must bind subscription ID and reason. |

**S3 — High: keyword scanning is advisory evidence, not the security boundary. Impact/effort 4/1.** P:1226–1298, P:2016. `іgnore previous instructions` (Cyrillic first letter) and ordinary polite requests are not detected. Conversely, legitimate discussion of `pay_order` can trigger a block. Only caller-supplied `untrustedContext` is scanned; omitting it avoids scanning a malicious ledger note. Exact trusted-email comparison correctly prevents many Unicode aliases from being trusted; casing passes, while whitespace causes false rejection, sometimes a spoof hard-block. Do not “fix” this by equating visual homoglyphs. Keep original evidence, optionally normalize a separate scanner view, retrieve notes from verified resources, and label results “No configured patterns detected.” Authorization must hold when scanner detection is always false. Bind trusted vendors to verified PayPal identity/account context; normalize email consistently for display/lookup and reject unsupported internationalized forms explicitly. A matching domain substring is a warning heuristic, not proof of fraud. Tests must include both benign technical text and zero-keyword attacks.

**S4 — Critical: approval neither authenticates the decision nor binds the executed payload. Impact/effort 5/2.** P:1903–1998. The purported SHA-256 is FNV-1a-like 32-bit hashing; subscription ID, currency, reason and other consequential parameters are omitted. The resolver compares two saved strings without recomputing. Reproduction: pause P2, change amount to 999 and recipient to `evil@example.com`, approve with its original hash, then approve the returned result again: both succeed and spend becomes 2,026. Changing the diff baseline to 777 also executes 777. There is no expiry, consumption, policy revision, account binding, resource freshness or authenticated human decision. Fix: persist an immutable pending record on the trusted executor; use real SHA-256 over the exact validated outgoing request plus account, environment, policy revision, evidence version, expiry and unique approval ID. The UI sends an approval ID and decision, never an authoritative evaluation object. Recompute, revalidate, atomically consume, reserve, then dispatch. A digest is an integrity check, not authentication; use an authenticated, CSRF-protected human route isolated from MCP. Test tampering of every consequential field, replay, double-click, stale policy/evidence and changed amendment.

**S5 — Critical for real execution: accounting lacks atomic reservations, persistent identity and full effect coverage. Impact/effort 5/3.** P:1041–1133, P:1552–1561, P:2043–2059. Sequential valid $39 calls are capped: 28 → 67 → 106 → 145, then pause. This is a working control, not a sequential-smurfing bypass. Negative calls reopen budget; ten $24 refunds on distinct nonexistent orders execute while spend remains 28. The rolling counter never expires, resets on reload/reset, and lacks durable multi-process protection. Subscription/dispute effects are not consistently bounded. The synchronous mock has no demonstrated concurrent race, but an asynchronous live implementation will need atomic check-and-reserve. Define a gross-outflow budget covering actual outgoing payments, refunds and dispute settlements; model recurring commitments separately. Never subtract refunds from spending headroom. Store account-scoped completed events plus pending reservations, with unique operation IDs. Retain reservations on uncertain network outcomes and reconcile before retrying. Use PayPal idempotency only where the endpoint supports it. [PayPal idempotency](https://developer.paypal.com/api/rest/reference/idempotency/).

**Exact validation primitives (Task 1 `src/types/money.ts`; Task 2 `src/constitution/directives.ts`).** Use these on fully extracted values; wire schemas must require USD and tool-specific fields. Zero is permitted for policy limits, not money transfers. Non-monetary cancellation has no invented amount. The compiler must catch any validation error and return an explicit invalid result; it must not activate a partial policy.

```ts
export function usdCents(value: unknown, allowZero = false): number {
  if (typeof value !== 'string' || !/^(0|[1-9]\d{0,11})(\.\d{1,2})?$/.test(value))
    throw new Error('INVALID_USD');
  const [whole, fraction = ''] = value.split('.');
  const cents = Number(whole) * 100 + Number(fraction.padEnd(2, '0'));
  if (!Number.isSafeInteger(cents) || cents < (allowZero ? 0 : 1))
    throw new Error('INVALID_USD');
  return cents;
}
export function requiredDirective(markdown: string, label: string): string {
  const prefix = `- ${label}:`;
  const values = markdown.split(/\r?\n/).filter(line => line.startsWith(prefix));
  if (values.length !== 1) throw new Error(`Expected one ${label}`);
  return values[0].slice(prefix.length).trim();
}
```

The complete compiler should allow only known headings, blank lines, one exact `Mode:` line, and known directive lines. Reject fences, HTML, unknown directives and extra prose in this constrained policy format. Parse tools by membership in a registry and reject unknown entries; use `[]` for an explicitly empty list. Parse percentage with a fully anchored decimal grammar and finite/range checks. Use integer basis points for percentage comparisons: `(proposedCents - baselineCents) * 10_000 > baselineCents * toleranceBps`, with safe-integer bounds or BigInt intermediates. Do not round percentages before deciding: the baseline rounds to one decimal and can admit small over-tolerance increases.

**Exact digest primitive (Task 6 `src/firewall/payload-hash.ts`).** Only schema-validated JSON may enter this routine; amounts are canonical decimal strings or integer cents, never rounded during hashing. Arrays retain order, object keys are sorted, unsupported/nonfinite values are rejected by validation. Hash the actual final request, including an amendment's changed body; retain the original proposal as a separate audit object.

```ts
type Json = null | boolean | number | string | Json[] | { [key: string]: Json };
function canonical(value: Json): string {
  if (value === null || typeof value !== 'object') {
    if (typeof value === 'number' && !Number.isFinite(value)) throw new Error('NONFINITE');
    return JSON.stringify(value);
  }
  if (Array.isArray(value)) return `[${value.map(canonical).join(',')}]`;
  return `{${Object.keys(value).sort().map(key =>
    `${JSON.stringify(key)}:${canonical(value[key])}`).join(',')}}`;
}
export async function payloadHash(envelope: Json): Promise<string> {
  const bytes = new TextEncoder().encode(canonical(envelope));
  const digest = await crypto.subtle.digest('SHA-256', bytes);
  return `sha256-${Array.from(new Uint8Array(digest), b =>
    b.toString(16).padStart(2, '0')).join('')}`;
}
```

**Executor contract, not an optional UI convention:** `executeApproved(approvalId, decision, authenticatedHuman)` loads the server-owned pending record; checks account/session, `PENDING` state, expiry, policy revision and hash; re-reads resources; rejects new hard blocks; builds and revalidates the selected final request; atomically changes pending→reserved with operation/resource/budget reservations; sends only that request; records confirmed success or `UNKNOWN`. Approval may override only explicitly listed soft holds within the displayed decision; it cannot bless invalid money, missing ownership or disabled tools. A changed amount/payee/resource requires a new preview and approval. If a tool cannot express a baseline amendment, do not render that action. An in-memory implementation can demonstrate this flow, but durable storage is required before real use.

**F1 — Reject the claimed universal security probability. **F2 — Prove budget safety conditionally by induction, not by screenshots. Impact/effort 5/2.** Let `S` be completed gross outflow in the rolling window, `R` pending/uncertain reservations, `a≥0` the verified proposed outflow, and `C` the active cap. Admit only if `S+R+a≤C` in one atomic account-scoped transaction. Reservation increases `R` by `a`; confirmed settlement transfers `a` from `R` to `S`, preserving the bound. Definitive failure releases `R`; unknown outcome retains it. If policy lowers C below existing commitments, block new admissions rather than pretending the invariant already holds. Refund/dispute effects and external account activity require reconciliation and defined coverage; without exclusive observation/control, claim only firewall-mediated outflow protection. **F3 — Cryptographic improvement is real but narrower than “unbreakable.” Impact/effort 5/1.** For an ideal b-bit hash, birthday collision probability is approximately `1−exp(−n(n−1)/2^(b+1))`. At b=32, about 77,163 values give 50% collision probability; FNV is not cryptographically secure anyway. SHA-256 vastly improves collision resistance, but the demonstrated approval exploit needs no collision at all. The essential fixes are recomputation, complete field binding, authenticated consent, freshness and one-time atomic consumption. Measure rejection of each mutation/replay case; do not equate a 64-hex digest with secure approval.

**F4 — Statistical evidence must specify sampling. Impact/effort 4/1.** The 27 cases are deliberately chosen counterexamples, not an IID sample and not a real-world bypass rate. Demonstrating at least 95% preset task-success with a one-sided 95% lower bound would require at least 59 independent representative successes with zero failures, plus a justified population/task definition. A convenience hackathon sample cannot establish population fit.
