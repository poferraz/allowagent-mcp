# Job’z Implementation Plan

> For agentic workers: use superpowers:executing-plans to implement this plan task by task. Native execution is recommended for this small, tightly coupled build and limited time budget. This document authorizes no external publication or spending. Steps use checkboxes for tracking.

**Goal:** Demonstrate a cleaner's AI-drafted bill, an owner-approved correction, and payment of the current revision through PayPal sandbox.

**Architecture:** A single FastAPI application serves a React UI and owns the billing ledger in SQLite. AI returns validated proposals; server services control approval and PayPal calls. A single merchant is configured through environment variables.

**Tech stack:** Python 3.12+, FastAPI, Pydantic, sqlite3, httpx, Groq SDK, pytest; Node 22.12+, React, TypeScript, Vite, Vitest, Playwright; Docker for reproducible running.

**Spec:** [Job’z MVP design](../specs/2026-10-07-jobz-design.md). Read it before executing. Research and submission links are in the root README.

## Global constraints

- Sandbox only; refuse startup with a live PayPal API host.
- One configured merchant, CAD only, English UI, fictional demo data only.
- Python 3.12+; Node 22.12+; one app process; SQLite WAL on durable storage.
- Monetary values are integer CAD cents; quantity_hundredths is an integer.
- Published invoice revisions are immutable; every mutation uses expected_revision.
- AI may propose; only authenticated owner actions change charges; only customer-approved server capture collects payment.
- No payment success from browser callbacks alone; verify the capture and its invoice binding.
- Text input is limited to 4,000 characters; audio is limited to 10 MB and 90 seconds.
- At most one open issue and one active payment attempt per invoice.
- No application secrets, real customer records, or real payment credentials in the repository or browser.

## Review focus

1. Payment times out after PayPal succeeds: reconciliation finds the original capture; no second payment (Task 2).
2. Customer begins paying revision 1 while owner corrects it: outdated capture is rejected or the in-progress payment freezes the correction (Tasks 2 and 5).
3. Spoken negation and missing rates: no inferred billable item or guessed amount (Task 4).
4. Private owner notes or another customer's link: no cross-role disclosure (Tasks 1 and 5).
5. AI outage, browser reload, or app restart: manual billing remains usable and durable payment state is preserved (Tasks 2, 4, and 6).

Define records in schemas.py before consumers use them: InvoiceLine, InvoiceDraft, InvoiceView, InvoiceRevision, InvoiceProposal, IssueView, ResolutionProposal, PaymentAttempt, PaymentStatus, CustomerGrant, OwnerSession, JobContext, SourceRef. UUIDs cross APIs as strings.
